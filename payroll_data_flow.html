Payroll Data Flow — From Pay Run to Financials

How Paylocity payroll data becomes the numbers leadership reviews — and where the gaps are

The Problem

During a recent monthly financial review, the Housekeeping salary line item came in over budget. When we checked the Payroll Budget vs Actuals report — built directly from Paylocity data — Housekeeping came in under budget in both gross pay and headcount. Both reports look at the same payroll, but show opposite results. This document maps every step of the data flow to explain why.

Path A — Payroll BvA

Fully automated. A Python script prorates pay across calendar months using exact pay period dates. Same logic, all 20 sites, every month. Penny-perfect math.

Path B — NetSuite Financials

Partially automated, partially manual. An automated feed posts by check date. Accountants at each site manually create journal entries to prorate — the same math done by hand across 20 sites by multiple people.

Key Finding

Both paths do the same thing — assign payroll to the correct calendar month. Path A does it with code (once, identically). Path B does it by hand (20 times, differently). The divergences result from these two approaches producing different numbers for the same payroll.

Step 2 Deep Dive: Automated Monthly Proration

When a pay period spans two calendar months, the script splits earnings proportionally by calendar days. Balanced rounding guarantees split pieces sum to the exact original amount.

What leadership sees
Stage 1: Automated GL Feed (Check Date Posting)

Paylocity posts JEs to NetSuite on the check date — regardless of the pay period. A paycheck issued February 1st covering January 20–31 posts entirely to February. Without manual accruals, the GL would be purely cash-basis.

Stage 2: Manual Payroll Accruals — The Primary Pain Point

Accountants create manual JEs to move payroll to the correct month — the same proration the BvA script does automatically, but by hand across 20 sites.

Why this creates divergence

Each accountant may use different rounding, day-count methods, or estimates from prior month payroll. Small differences × 20 sites = meaningful department-level divergence.

How the Rules Work

Paylocity processes rules sequentially — later rules override earlier ones:

1. Setup Rules (S-*) — set cash account, map Sub Dept → GL cost center

2. Earnings Rules (E-*) — assign GL debit account per paycode. Default = 600050

3. Tax Rules (T-*) — employer/employee tax codes → tax GL accounts

4. Deduction Rules (D-*) — benefits, 401k, garnishments → liability/expense accounts

5. Miscellaneous Rules (M-*) — block specific codes from GL entirely

Paycode Mapping — Complete Classification

Every Paylocity earnings paycode with its Google Sheet classification alongside the actual GL Rules destination. 211 total codes (earnings, taxes, deductions). Mismatches that need resolution are flagged.

How to Read This Tab

The Pay Classification and Finance Category columns come from the Google Sheet — this is how the BvA pipeline classifies each code. The GL Rules Destination column shows where Paylocity actually posts the money in NetSuite.

We flag codes where these two sources disagree in a way that matters:

Hits Salary but Not Salary-Equivalent — Code defaults to GL 600050 (salary) but is mapped to a non-salary category (Benefits, Bonus, Stipend, etc.). This means non-salary expense is inflating the salary line in the financials.

Blocked in GL — Code is removed from the GL entirely by Paylocity rule M-4000. If it carries dollar amounts in the BvA, it creates a gap between BvA GP and GL 600050.

Either the GL Rules need an override to route these elsewhere, or the paycode mapping needs to reclassify them as salary-equivalent.

Action Items for Controller Review

Pipeline Changes (Next Claude Code Session)

1. Blocked codes sourced from GL Rules Export. Reconfigure gl_bridge.py to read rule M-4000 from the GL Rules Export file instead of the Google Sheet flags. The GL Rules file is the authoritative source for what Paylocity actually blocks from the GL. Only codes with Finance Category = "Gross Pay" in the live mapping need a bridge adjustment (others are blocked but have no GP impact).

2. Cross-category codes derived by cross-reference. gl_bridge.py identifies cross-category codes programmatically: any code where Finance Category ≠ Gross Pay in the live mapping AND the GL Rules have no earnings override (meaning the code defaults to 600050). Currently 15 codes.

3. Auto-populate output columns in Google Sheet. On each pipeline build, write three output columns to the Google Sheet (after the existing input columns A–F). Headers should clearly indicate these are derived outputs, not editable inputs:

Column G: ⟶ [OUTPUT] GL Account — actual GL destination from GL Rules

Column H: ⟶ [OUTPUT] Bridge Classification — Standard / Blocked / Cross-Category / Outside Bridge

Column I: ⟶ [OUTPUT] Bridge Impact — Subtract from GP / Add to Expected GL / No adjustment

4. Rename existing Column G. The current "Blocked or Cross Category" column should be removed or renamed to make room for the output columns. The pipeline will overwrite columns G–I on every build.

The Core Issue: Same Math, Different Execution

Both paths answer: "How much payroll expense belongs in each calendar month?"

Path A: one automated script — calendar-day proration, penny-perfect, identical for every employee at every site.

Path B: individual accountants at 20 sites manually calculate and post JEs — same proration by hand, no standardized template.

Result: opposite conclusions from the same payroll.

Divergence Sources — Ranked

1. Manual accrual differences. Each accountant's proration differs from automated calculation.

2. Dept reclassification JEs. Accounting moves salary between depts in GL; BvA doesn't see it.

3. COGS-routed departments. Sub Depts 91000/93000/94000 hit COGS, not 600050.

4. Dept routing differences. GL feed uses Sub Dept codes; BvA uses BOD crosswalk.

5. Timing and corrections. Late JEs, accrual reversals, one-time fixes.

Updated Diagnosis

GL mapping rules are clean, standardized, consistent. The automated feed is not the problem. Divergence is primarily manual accrual differences and dept reclassification JEs, with a potential factor from COGS-routed depts.
